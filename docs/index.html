One request becomes 16 moving parts

The progress bar is not decoration. Its three regions mirror the actual transfer pipeline: probe, parallel shards, verify.

01

1probe

A Range request asks one question before the file is cut: can this server serve byte ranges?

02

16shards

Sixteen segments move at once. Work stealing takes the remaining block away from a slow connection.

03

1verify

Every returned range is checked, then the merged file is checked against the expected byte count.

  1. PROBE

    Range support is settled first. If the server cannot do it, the engine stops pretending and downloads straight through.

  2. SCHEDULE

    The block count is about four times the connection count, so a slow worker never owns the last remaining piece.

  3. VERIFY

    The bytes returned are compared with the range that was asked for; the merged file is compared with the total size.

Six decisions baked into the byte plane

MechanismOperational consequence
Segmented parallel downloadHTTP Range segments downloaded in parallel, with connection reuse (HTTP/2 multiplexing + keep-alive).
Dynamic segmentation + work stealingFine-grained pre-splitting plus work stealing, so one slow connection cannot drag the whole transfer down — and the "last segment on a single thread" long tail disappears.
Restrained adaptivityConcurrency drops only on 429/503 or after consecutive failures. Ordinary jitter never touches the thread count — no AIMD oscillation.
Resume from real progressSegments are persisted on disk; pause/resume continues from what actually landed, not from a remembered number.
Range tampering rejectedThe bytes actually returned are checked against the Range that was requested — a server that ignores Range and sends the whole file is caught, not written as misplaced data.
Byte-level integrity checkTotal size is verified after the merge step; a short or oversized result is rejected.

Each line is measurable in the repository. Two exist because the obvious implementation was measured and rejected.

Every control maps to a public field

Five controls below use the engine defaults. The switch is live in the page; the numeric consequences come from measured runs.

dynamicSegmentation

Split work finer than the connection count.

About four blocks per connection, so the final stretch is never one worker on its own. Off: fixed blocks plus work stealing.

ON BY DEFAULT

tailAssist

Give the tail to whatever is idle.

At most two splits per segment in the endgame; nothing below 2 MiB is split, so a 16 MiB block tops out at four parts.

ON BY DEFAULT

overlapMerge

Merge while the last bytes arrive.

Measured on 512 MB / 64 connections: 11.08 s to 10.39 s, about 6%. It can duplicate a write with tail assist, so it stays off.

OFF BY DEFAULT

bufferedSegmentWrite

Write segments through a buffer.

16 MB / 128 connections / 64 KB segments: 2576 ms direct, 2584 ms buffered. The 0.3% difference is noise; resume stays honest without it.

OFF BY DEFAULT

trustAllCerts

Trust any certificate.

Packet-capture debugging only. It turns certificate validation off, so production keeps it off.

OFF BY DEFAULT

Questions before the first download

Does this need Android?

No. It is a pure Kotlin/JVM library. Android is one consumer; a server or desktop tool is another. The only requirement is JVM 17+.

Do I have to use the plugin framework?

No. turbodl-core has no plugin-framework dependency. The framework earns its place only when you need protocols beyond HTTP.

Can it download HLS?

Yes for video-on-demand through the official plugin: playlist resolution, concurrent segments and AES-128. Live playlists, DRM and fMP4 are refused explicitly.

Is there a GUI?

Not from this project. The SDK deliberately renders no interface. What ships is the engine, the plugin framework and a command-line tool.

Where do I get the files?

Every file is an attachment of the v0.2.4.0 release: a self-contained CLI JAR and an offline Maven bundle. They are not on Maven Central yet.

What happens when a server lies about Range?

The returned bytes are compared with the requested range. A server that ignores Range is caught and that segment fails instead of writing misplaced bytes.
