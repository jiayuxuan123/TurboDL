One file, three stages

1 request

First, one request asks whether the server honours Range.

16 in flight

Then sixteen segments are in flight; work stealing keeps one slow connection from holding up the rest.

1 pass

Finally the parts are merged and the byte count is verified.

The bar is the engine's own progress bar, enlarged until it spans the page. Its widths follow the real amount of work in each stage, not a decorative ratio.

  • Ahead of the requestA Range probe settles whether the server can serve byte ranges at all. If it cannot, the engine stops pretending and downloads straight through.
  • While it runsBlock count is about four times the connection count, so a slow connection never owns the last remaining piece of work.
  • Before it says doneThe bytes actually returned are checked against the range that was asked for, and the merged file is checked against the total size.

Six things it does to the bytes

WhatHow
Segmented parallel downloadHTTP Range segments downloaded in parallel, with connection reuse (HTTP/2 multiplexing + keep-alive).
Dynamic segmentation + work stealingFine-grained pre-splitting plus work stealing, so one slow connection cannot drag the whole transfer down — and the "last segment on a single thread" long tail disappears.
Restrained adaptivityConcurrency drops only on 429/503 or after consecutive failures. Ordinary jitter never touches the thread count — no AIMD oscillation.
Resume from real progressSegments are persisted on disk; pause/resume continues from what actually landed, not from a remembered number.
Range tampering rejectedThe bytes actually returned are checked against the Range that was requested — a server that ignores Range and sends the whole file is caught, not written as misplaced data.
Byte-level integrity checkTotal size is verified after the merge step; a short or oversized result is rejected.

Each line can be checked against the repository; they are not feature names. Two of them exist because the obvious version was measured and turned out wrong.

Every knob is a public config field

Five of them are switches you can flip right here; the state matches the engine's defaults, and the numbers in the answers are measured, not estimated.

Split the work finer than the connections.

dynamicSegmentation · default on

Block count runs about four times the connection count, so the last stretch is never one connection on its own. Turn it off and you get fixed blocks with work stealing.

Hand the tail to whatever is idle.

tailAssist · default on

Only in the endgame: at most 2 splits per segment, nothing under 2 MiB is split, so a 16 MiB block becomes at most 4. Splitting earlier would only raise the request count.

Merge while the last bytes are still arriving.

overlapMerge · default off

Measured on 512 MB / 64 connections: 11.08 s down to 10.39 s, about 6%. With tail assist on it can write the same range twice, so it stays off by default.

Write segments through a buffer.

bufferedSegmentWrite · default off

A/B on 16 MB / 128 connections / 64 KB segments: 2576 ms direct against 2584 ms buffered, 0.3% inside the noise. Resume reads the file length, so buffering would blur what landed on disk.

Trust any certificate.

trustAllCerts · default off

For packet-capture debugging only: it turns certificate validation off. Production keeps it off, and the default does.

The plugin framework keeps the same discipline on its Kotlin side: a script may compute URLs, headers and signatures, but it never touches the download stream.

Questions that come up first

Does this need Android?

No. It is a pure Kotlin/JVM library — the Android app is one consumer, a server or a desktop tool is another. The only requirement is JVM 17+.

Do I have to use the plugin framework?

No. turbodl-core does not depend on it: embed the engine and stop there. The framework earns its place only when you need protocols beyond HTTP.

Can it download HLS?

Yes for video-on-demand, through an official plugin: playlists are resolved, segments are fetched concurrently and AES-128 is decrypted. Live playlists, DRM and fMP4 are refused explicitly instead of producing a file that looks fine and is not.

Is there a GUI?

Not from this project. The SDK renders no interface of its own — that is deliberate. What ships is the engine, the plugin framework and a command-line tool.

Where do I get the files?

Every file is an attachment of the v0.2.2.0 release: a self-contained CLI JAR and an offline Maven bundle. They are not on Maven Central yet, and the download page says so rather than pretending otherwise.

What happens when a server lies about Range?

The bytes actually returned are compared with the range that was requested. A server that ignores Range and answers with the whole file is caught, and that segment fails instead of writing misplaced bytes into the output.
