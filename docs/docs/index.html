What a plugin manifest looks like

A plugin is a JAR plus this file. The reference page lists every field, its type, whether it is required, and the allowed values.

turbodl-plugin.json

{
  "manifestVersion": "1.0",
  "id": "parser.example",
  "name": "Example parser",
  "description": "Turns example:// links into download requests.",
  "version": "0.1.0",
  "author": "you",
  "homepage": "https://github.com/you/turbodl-plugin-example",
  "license": "MIT",
  "category": "turbodl-parser",
  "capabilities": [
    "dev.turbodl.cap.parser"
  ],
  "protocols": [
    "example"
  ],
  "turbodl": {
    "apiMajor": 1,
    "requiredApiVersion": "1.0.0"
  },
  "entry": {
    "language": "kotlin",
    "pluginClass": "com.example.ExamplePlugin"
  },
  "extensionPoints": [
    "turbo.linkParser"
  ]
}

The same file the manifest reference renders, so the two pages cannot disagree.

Architecture

Three rules decide every design question in this project:

  1. core works alone. turbodl-core is a complete engine with zero plugin dependency; plugins are strictly additive.
  2. the kernel is only mechanism. It knows no protocol — lifecycle, cleanup, event bus, service registry, extension points, version handshake, diagnostics.
  3. dependency direction is strict. runtime → core, never the reverse.
