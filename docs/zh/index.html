一个文件， 三段

1 次请求

先发一个请求，问服务端认不认 Range。

16 个在飞

然后 16 个分片同时在飞；工作窃取让一条慢连接拖不垮其余的。

1 次校验

最后合并这些分片，并核对总字节数。

这条就是引擎自己的进度条，被放大到整幅宽度。各段宽度按每段真实的量分配，不是装饰性的比例。

  • 请求之前先用一个 Range 探测确认服务端到底能不能按字节范围给数据。不认就不假装认，直接整条下载。
  • 下载进行时块数大约是连接数的四倍，所以某条慢连接不会独占最后剩下那点工作。
  • 说完成之前核对服务端实际返回的字节是不是请求的那段，合并后再核对总大小。

它对字节做的六件事

做什么怎么做
分片并发下载按 HTTP Range 并行下载分片，并复用连接（HTTP/2 多路复用 + keep-alive）。
动态分片 + 工作窃取细粒度预分片 + 工作窃取：一条慢连接拖不垮整个传输，也消除了「最后一个分片单线程收尾」的长尾。
克制的自适应只在遇到 429/503 或连续失败时才降低并发。普通抖动绝不改线程数 —— 不做 AIMD 来回震荡。
按真实进度续传分片状态落盘；暂停/继续按磁盘上真实写完的字节接着下，而不是按记忆中的数字。
拒绝 Range 篡改会核对服务端实际返回的字节是否就是请求的那段 Range —— 忽略 Range 直接回整文件的服务端会被识别出来，而不是把错位数据写进文件。
字节级完整性校验合并完成后校验总大小；少了或多了都判为失败。

每一条都能在仓库里核对，不是功能名词。其中两条存在的原因，是「看起来显然」的做法被实测否掉了。

每个旋钮都是公开的配置字段

其中五个是你可以直接按的开关；开关状态与引擎默认值一致，答案里的数字是实测的，不是估计的。

把工作切得比连接更细。

dynamicSegmentation · 默认开启

块数约为连接数的四倍，收尾阶段不会只剩一条连接在干活。关掉它则退回固定块大小 + 工作窃取。

把尾巴交给闲着的连接。

tailAssist · 默认开启

只在收尾阶段生效：每个分片最多拆 2 次，低于 2 MiB 不拆 —— 16 MiB 的块最多变成 4 段。更早拆分只会抬高请求数。

最后几个字节还在路上时先合并。

overlapMerge · 默认关闭

512 MB / 64 连接实测：11.08 s 降到 10.39 s，约 6%。但与收尾托管同时开启时可能重复写同一段，所以默认关闭。

分片写入走缓冲流。

bufferedSegmentWrite · 默认关闭

16 MB / 128 连接 / 64 KB 分片实测：直写 2576 ms、缓冲 2584 ms，0.3% 落在噪声里。续传按文件长度判断进度，缓冲只会让「已落盘」变模糊。

信任任何证书。

trustAllCerts · 默认关闭

只给抓包调试用：它会关掉证书校验。生产环境保持关闭 —— 默认就是关的。

构件作用必需？
turbodl-core下载引擎本体
分片并发下载、断点续传、重试、限速、DNS/代理。可单独使用，不依赖插件框架。		必需
turbo-plugin-runtime插件运行时内核
生命周期、清理（disposer）、事件总线、服务注册表、扩展点、版本握手、诊断。对任何具体协议一无所知。		可选
turbo-plugin-bootstrap基础装配
一次调用装配基础插件（Kotlin 加载器 + HTTP 后端），并桥接引擎的事件流。		可选
turbo-plugin-hlsHLS VOD 适配
解析 M3U8 清单、分片并发下载（分片级重试）、AES-128 解密、支持 EXT-X-BYTERANGE。直播/DRM/fMP4 清单会被明确拒绝，而不是产出一个损坏的文件。		可选
turbo-plugin-jsJavaScript 插件加载器
加载用 JavaScript 写的 TurboDL 插件。内嵌 QuickJS —— 每个脚本一个 runtime 与 context —— 并给脚本一套稳定的 `host`/`plugin` ABI。		可选
turbo-plugin-parser平台链接解析
把分享链接变成可下载请求：微博（MP4 + 图集）、小红书（无水印视频 + 原图）、Pixiv（每页原图）。不持有任何凭证 — 平台需要登录时返回 null，由宿主自己的会话处理接手。		可选
turbodl-cli命令行工具
基于 SDK 的完整命令行工具：多线程、断点续传、批量、给脚本与 Agent 用的 NDJSON 输出。以 fat JAR 形式提供。		可选

一个仓库里六个构件：引擎可以单独取走，其余是主动加进来的。思路层面的致谢：aria2、XDM、axel、Persepolis、Motrix、ab-download-manager —— 未复制任何源码。

它拒绝做什么

不支持的流会响亮地失败。另一种做法 —— 写下一个看起来正常、其实不对的文件 —— 正是这一节要避免的失败方式。

插件明确拒绝为什么
HLS VOD Backend
backend.hls		直播清单（没有 `EXT-X-ENDLIST`）DRM / `SAMPLE-AES`fMP4 `EXT-X-MAP`不连续标记明确拒绝：不支持的流直接失败，而不是产出一个看起来正常、其实不对的文件。
JavaScript Plugin Loader
loader.js		注册 `DownloadBackend`（字节面留在 Kotlin 一侧）发布服务（服务是 Kotlin 对象图）`require` / npm / `fetch` —— 宿主 ABI 就是全部可用面`jar:` 与远程脚本源（目前只支持本地文件 / `inline:` / `data:`）脚本负责算 URL、请求头和签名，从不经手下载数据流。这条边界正是它不会变成带宽瓶颈的原因。
Platform Link Parser
parser.platforms		登录 — 需要会话的平台返回 null，由宿主自己的账号处理接手Pixiv 动图（ugoira）：zip + 帧时长表需要图像处理Pixiv 小说需要签名的接口（抖音 / 快手 / B站）：各自的签名算法仍留在宿主侧它的结果类型不含任何路径：`DownloadRequest` 需要 `destination: File`，而解析发生在宿主决定目录之前。临时目录占位只在边界处补上，宿主仍然走自己的路径策略。

插件框架在 Kotlin 一侧同样克制：脚本可以算 URL、请求头与签名，但从不经手下载数据流。

最先被问到的几件事

它需要 Android 吗？

不需要。它是纯 Kotlin/JVM 库 —— Android 应用只是使用者之一，服务端或桌面工具同样可以用。唯一的运行要求是 JVM 17+。

必须用插件框架吗？

不必。turbodl-core 不依赖它：只用引擎就停下也可以。需要 HTTP 之外的协议时，这个框架才有意义。

能下 HLS 吗？

点播可以 —— 通过官方插件：解析清单、分片并发、AES-128 解密。直播清单、DRM 与 fMP4 会被明确拒绝，而不是产出一个看起来正常、其实不对的文件。

有图形界面吗？

这个项目不提供。SDK 自己不画任何界面 —— 这是有意的。提供的是引擎、插件框架与一个命令行工具。

从哪里拿文件？

每个文件都是 v0.2.4.0 这个 Release 的附件：一个自包含的 CLI JAR 和一个离线 Maven 包。它们还没有发布到 Maven Central —— 下载页如实写明，不假装有。

服务端对 Range 撒谎会怎样？

会核对实际返回的字节与请求的那段是否一致。忽略 Range、直接回整文件的服务端会被识别出来，该分片判为失败，而不是把错位的数据写进文件。
