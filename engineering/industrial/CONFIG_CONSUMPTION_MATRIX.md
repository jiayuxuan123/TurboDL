## 0. 判定口径

- “直接读取/消费”只列生产源码中的读取点、参数传递点或直接决定运行行为的符号；CLI 赋值和插件桥接单独注明。
- “未找到”表示在主源码和已检查插件源码中未找到该字段的运行时读取点，不根据注释或字段名推断已生效。
- “最接近测试”只表示该测试覆盖了相邻行为，不等同于该字段的完整契约测试。
- 测试名保留源码中的 Kotlin 标识符；中文测试名按原样引用。
- 当前 `TurboClient.backendFor()` 先问 resolver，再无条件回退内置后端；内置裸 HTTP 路径与 HLS 插件路径的消费范围不同，表中分别标明。

## 5. 阻塞项排序

### P0：会静默忽略

1. **CFG-45 `maxStallRecoveries`**：生产源码只声明和校验，未找到读取点；现已显式标 `@Deprecated`，说明现代调度器按单分片取消并由 `maxRetries` 收尾。CLI/旧消费者仍可传，但不得再宣称它控制任务级失败次数。
2. **CFG-06 `dynamicSegmentation`**：旧字段现已作为 `effectiveTailAssist = tailAssist && dynamicSegmentation` 的兼容开关被真实读取；`ConfigConflictTest` 覆盖显式 false 必须关闭收尾托管。它不是完整动态分段总开关，文档需要避免扩大语义。
3. **CFG-10 `overlapMerge`**：已标 `@Deprecated` 且生产源码不读，但 CLI 仍提供 `--no-overlap`；`ConfigConflictTest` 的本地 helper 没有验证生产 no-op。
4. **REQ-08 `tags`**：引擎不读取，只有 `Created` 事件带原始 request；其他事件没有 tags，不能支持“所有事件原样取回”的宽泛解释。
5. **REQ-09 `mirrors` 在插件路径**：内置 HTTP 已消费；HLS 未找到镜像消费点，JS bridge 不映射 mirrors。宿主经 JS/HLS 路由时可能静默丢失该字段。

### P1：注释与行为冲突

1. **CFG-26 `maxConnectionsPerHost`**：多镜像路径已按每个来源独立限流，`MirrorPool.pickWithLimit()` 原子领取避免并发超发；仍需验证 probe/预热/重试是否被同一计数覆盖。
2. **CFG-30 `warmUpConnectionCount`**：源码/API 注释说 `<=0` 取 `min(maxConnectionsPerTask, 8)`，实现取当前 connections 再和 `warmUpMaxParallel`/预算取小。
3. **CFG-32 `slowStartInitial`**：注释说 `<=0` 从 `maxConnectionsPerTask` 起跑，实际 0 在 UPWARD、DOWNWARD、普通慢启动分支中分别有不同起点。
4. **CFG-23 `maxIdleConnections`**：注释称“应 ≥ maxConnectionsPerTask”，实现却用 `maxOf` 静默抬高，低于任务连接数的配置没有错误或告警。
5. **REQ-02 取消测试名与断言**：`BuiltinBackendE2ETest.取消后任务从进度表里消失` 实际断言任务仍在进度表且状态为 CANCELED，也没有断言 `deleteOutput=true` 删除文件。

### P2：安全 / 数据完整性风险

1. **REQ-07 `stableKey` 路径安全边界**：碰撞和同 key 并发双写已通过摘要后缀与租约修复；仍缺超长路径、符号链接和工作目录权限的矩阵测试。
2. **REQ-09 同大小异内容镜像**：当前硬校验主要是大小和每个分片的 `expectedTotal`，没有全文件内容一致性；跨源头隔离已覆盖，但镜像内容污染仍需 `expectedSha256`/更强校验或明确风险提示。
3. **REQ-01 非 HTTP 主源**：构造器不校 scheme，内置后端回退路径也不检查 `supports` 结果；`file://`、相对 URL 和插件 scheme 可能在更深层失败，错误分类不稳定。JS descriptor 已单独校验，裸 SDK 未统一。
4. **REQ-02 目标文件已存在/取消删除**：长度和 SHA 有校验，但已有目标文件的覆盖、续传、只读/目录权限和 `deleteOutput` 的副作用仍缺完整测试。

### P3：资源预算风险

1. **CFG-03/DER-06 “全局连接预算”作用域**：`ConnectionBudget` 建在每个 `TurboClient` 内；HLS 使用自己的 `Semaphore`，不共享该预算。多个 client 或多后端实例可以叠加突破用户配置。
2. **CFG-38/CFG-39/DER-03 缓冲总预算**：极端配置 `64 × 256` 触发 8 KiB 保底，源码注释已承认约 128 MB，超过默认 32 MiB 名义预算；现有测试将此作为“可知上界”，没有拒绝或失败。
3. **CFG-23 `maxIdleConnections`**：空闲池被静默抬高，配置值失去上限意义；连接池、HLS client 和 JS client 各自持有池，缺少统一资源观测。
4. **CFG-35/CFG-30 预热**：预热受多重裁剪，且 `warmUpConnectionCount<=0` 的实际上界与 8 的注释不一致，弱网设备上可能出现预期外的并行握手峰值。

## 6. 结论

- 46 个 `TurboConfig` 字段和 9 个 `DownloadRequest` 字段已逐项建立源码消费链。
- `CFG-06 dynamicSegmentation` 已接线为收尾托管兼容开关；`CFG-45 maxStallRecoveries` 和 `CFG-10 overlapMerge` 是已弃用兼容字段，不得继续宣称生效。
- 字段本身“有消费”不等于契约完整：`maxConnectionsPerHost` 仍需覆盖 probe/预热/重试计数，`warmUpConnectionCount`、`slowStartInitial` 仍有注释与分支语义待冻结。
- `Metadata.resolvedUrl` 和 `supportsRange` 已由内置 HTTP 通过新增的 `reportResolvedMetadata` 返回真实值；旧 `reportMetadata` 仅保留二进制兼容。插件 backend 的适配仍待补。
- 数据完整性下一步优先补测目标文件的符号链接/权限、同大小异内容镜像和弱校验器稀疏采样边界；资源预算最需要优先补测的是多 client、多后端和 64×256 缓冲保底。
